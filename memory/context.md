# 需求与取舍

## 原始需求

1. 基于 opencode 做一个自己的 harness，**非大改**。
2. 有体系的记忆系统，参考 ECC（skills / instincts / memory / hooks）。
3. 尽量全量汉化，包括内置 skill；MiMo-Code 已有部分汉化可参考。
4. 选择 CLI 还是桌面端，以及是否有其他方案。

## 最终选择

- **基线**：MiMo-Code（opencode 的衍生项目），因为它已经有 `MEMORY.md`、checkpoint、notes、FTS5、`/dream`、`/distill`，比从 opencode 裸起点更接近目标。
- **形态**：CLI/TUI，不做桌面端。opencode 是 server + client；桌面端只是多一个 Electron 客户端和一套 UI 字符串，不解决记忆/汉化需求。
- **仓库**：独立新仓库，保留上游只读快照 `_upstream_mimo/`，不自动合并上游。
- **改名**：第一方标识全面 ymcode；外部 Xiaomi MiMo provider/model、opencode 上游、第三方品牌保留。
- **记忆**：保留 MiMo 闭环，新增 evidence + confidence 的 instincts 中间层；不新增数据库表，不换存储。
- **汉化**：界面 + 内置技能正文 + 提示词/工具描述中文；代码标识符、内部日志、命令、路径英文。

## 关键约束（来自用户）

- 回复正文用中文；代码、命令、路径、判据标记不翻译。
- 放行的清单一次做完，不要拆成阶段计划；只有红线/不可逆操作才停下等确认。
- 不要用“确定”措辞承诺收益；实测高于统计先验；不要擅自放宽验收规格。
- 不要编造标识符/URL；404 的第一假设是“不存在”。
- 凭据不写入仓库，也不要打印进会话；需要认证时由用户输入。
- 重要操作写进项目权威记录，不只对话汇报。
- 独立复核要分工取证：静态/数值与运行时/像素分开。
- 不要用“跳过测试”冒充全绿；要区分“功能失败”和“环境清理失败”。

## 非目标

- 不做桌面端。
- 不重写 checkpoint/dream/distill，不引入向量数据库。
- 不翻译内部日志、异常堆栈、代码标识符、JSON 字段、路径。
- 不自动合并上游；不做完整的品牌重命名（外部 provider/上游/第三方保持原名）。
- 不把用户个人记忆文件复制进项目；本项目 memory 只存构建交接上下文。

## 成功标准

- 能构建、启动、完成一次会话。
- conscious memory：checkpoint 后能生成 candidate，能手动晋升，重启后 active 规则可注入。
- 汉化门禁全绿，核心界面/技能/提示词中文。
- 旧数据能安全迁移，旧目录保留。
