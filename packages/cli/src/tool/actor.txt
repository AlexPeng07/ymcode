启动一个新的 actor（子代理），自主处理复杂、多步骤的任务。

**子代理限制：** 当你以子代理身份运行时，你只能使用
`actor send` 与父智能体通信。其他动作（spawn、run、
cancel 等）仅限主智能体使用。使用 `actor send` 并通过
to_actor_id="main" 向父智能体汇报进度、发现或阻塞问题。

JSON 调用会把动作负载包装在 `operation` 对象内；`action` 是判别字段。

**`spawn` 是默认方式。** 它在后台启动子代理并立即返回
其 actor_id，因此多个子代理可以并行运行，而你在它们工作期间
仍能继续回应用户。`run` 会等待子代理的结果直到
完成、用户输入或超时——它是罕见的例外，不是常规路径。

示例：
{"operation":{"action":"spawn","subagent_type":"explore","description":"Find error recovery","prompt":"<full task>"}}
{"operation":{"action":"spawn","subagent_type":"explore","description":"Investigate T4","prompt":"<full task>","task_id":"T4"}}
{"operation":{"action":"status","actor_id":"<existing>"}}
{"operation":{"action":"wait","actor_id":"<existing>"}}
{"operation":{"action":"cancel","actor_id":"<existing>"}}
{"operation":{"action":"send","to_actor_id":"<existing>","content":"<message>"}}
例外情况——`run` 会阻塞对话；仅用于决定当前回合走向的极小查询：
{"operation":{"action":"run","subagent_type":"explore","description":"One tiny blocking lookup","prompt":"<full task>"}}

## 操作（由 `operation.action` 字段选择）

- spawn:  **默认方式。** 在后台启动子代理；立即返回 actor_id，
          使工作并行推进、你的回合保持可响应。
          几乎所有委托都用它：调查、分析、评审、
          实现、长搜索——任何需要真实耗时的工作。
          必需：subagent_type、description、prompt
          可选：command
- run:    **罕见例外。** 相同的启动方式，但会在行内等待结果直到
          完成、用户输入或超时。仅当你没有该结果
          就无法在本回合做出下一个决定，且工作是
          极小、快速、严格阻塞的查询时才允许。绝不要用 `run` 做
          常规分析、评审或实现工作——那些交给 `spawn`。
          如果不确定，用 `spawn`。与 `wait` 一样，用户输入或超时都会返回
          actor_id 和最新执行快照，且不会取消子代理。
          被中断后先处理用户；不要立刻再次等待。
          超时是固定的等待期限，不是失败或取消信号。
          在决定 send、wait 或 cancel 之前，先检查 status 和具体输出。
          必需：subagent_type、description、prompt
          可选：timeout_ms、command
- status: 非阻塞地轮询 actor 状态。必需：actor_id。
          返回：{ status: "pending"|"running"|"idle"|"unknown", executionState, actor_id, turnCount, ... }
          用 executionState 区分 running、completed、failed、cancelled 和 stopped。
          "idle" 只表示未在执行；不表示任务已完成。
          "stopped" 表示没有活动执行，也没有记录终止结果。部分文本或
          turnCount 不是完成的证据。不要承诺待定的完成通知；
          适当时使用 send 恢复未完成的工作。只有 "completed" 才确认成功。
- wait:   阻塞直到 actor 完成（成功/失败/已取消）或超时（默认 10 分钟）。
          必需：actor_id。可选：timeout_ms。
          返回：{ status, executionState?, actor_id, result?, error? }；同样的完成规则适用。
- cancel: 停止运行中的 actor（优雅停止）。必需：actor_id。幂等。
- send:   将消息投递到另一个 actor 的收件箱，唤醒它再进行一个回合。
          必需：to_actor_id、content。
          可选：to_session_id、type（默认 "text"）。
          接收方在下一轮迭代中会看到包装为 <inbox from="..." sent_at="...">...</inbox> 的消息。
          排队后即返回，而不是在唤醒的回合结束时返回——该回合的结果会以完成通知形式到达。

## 何时使用 actor

- **并行化（常规情况）**：一次性 `spawn` 所有独立的搜索/分析，让它们
  并发运行；稍后通过通知收集，或在必须同步时用 `wait`/`status`。
- **隔离繁重工作**：为 10 个以上文件的读取 `spawn` 一个子代理；你只拿到综合结论。
- **专用搜索**：使用 `explore` 进行只读代码发现（查找定义、调用方）。
- **定制评审**：`general` 子代理会不带偏见地对照规格验证实现。
- **处理受跟踪任务**：当你为某个活动任务（T1、T2、……）spawn 子代理执行工作时——调查、聚焦评审、专门实现——传入 `task_id`，使子代理的逐字发现被记录到 `tasks/<TID>/progress.md`。只传入 Task 工具在本次会话中返回的任务 ID；绝不要杜撰。如果你还没创建任务，先用 Task 工具创建，或省略 `task_id` 做临时 spawn。
- **完全不要委托的情况**：琐碎的单文件查找、已在上下文中的答案，或基于部分输出的决策。

## 收集已 spawn 的工作

`spawn` 交给你一个 actor_id，而不是结果。有三种取回结果的方式：

- **通知（首选）**：后台子代理完成时，其结果会作为通知出现在
  本次对话中。它运行期间继续工作。主回合结束前，
  引擎会等待活动子代理并将它们的通知返回给循环。
  每个自动等待窗口都有固定的 10 分钟期限；活动和部分完成
  不会延长期限。超时后，控制权连同仍活动的 actor ID 返回主智能体：
  检查 status 和可用结果，通过 send 请求具体进度或部分结果，
  或在必要时 cancel 并确认执行已退出。不要盲目重复等待。
  用户输入可以中断该等待而不取消子代理；先处理输入。
  处理新的用户输入后再次等待会重新开始一个窗口。
- **`wait`**：仅当你确实没有其他工作、必须在继续前拿到该结果时，
  才对单个 actor_id 阻塞。`timeout_ms` 限制的是这次等待，而不是 actor
  的执行；超时和用户输入中断都不会取消 actor。两者都包含
  最新执行快照。
- **`status`**：非阻塞的执行快照。`executionActive` 反映的是活动 fiber 或
  等待挂接的已预留执行，而不是持久化的 running 标签。已完成的
  fiber 是非活动的，即使其 Runner 仍报告 busy。`executionState: stopped` 表示
  没有活动执行，也没有可信的终止结果；绝不要把它当作成功。
  当新的执行处于活动或孤立状态时，旧的 outcome/error/result 字段会被省略。

扇出再扇入：在一条消息中 `spawn` 2-3 个子代理，然后依次对每个 `wait`。

## 编写提示词

你是子代理唯一的简报——它没有看过本次对话。
- 解释你试图达成什么以及为什么。
- 说明你已经了解或排除了什么。
- 为判断留出足够的上下文，而不只是狭窄的步骤。
- 如果需要简短输出，就明说（"用 200 词以内汇报"）。
- 对于调查：交出问题本身；规定的步骤会成为累赘。

## Actor ID 与 Task ID

`actor_id` 标识一个活动的子代理。它由 `spawn`/`run` 返回，并被
`status`、`wait`、`cancel` 和 `send` 接受。任务 ID（T1、T2、……）来自 Task 工具——只传入你在本次会话中通过 Task 工具调用得到的 `task_id`。如果 `task_id` 格式错误或未知，绑定会被丢弃：子代理的发现不会记录到任何任务，工具结果会告诉你这一点。

## 跟进已有的子代理

要给你已经有的子代理更多工作，`send` 一条消息：

  `{"operation":{"action":"send","to_actor_id":"explore-1","content":"<follow-up>"}}`

`send` 会把你的消息追加到该子代理自己的历史中，并唤醒它再进行一个
回合，因此它会保留此前的每条消息和工具输出——包括已经进入空闲状态的
子代理。消息一入队它就返回；被唤醒回合的
结果会以完成通知的形式到达你。

## 将子代理绑定到任务

当你 `spawn`（或例外地 `run`）一个为特定任务工作的子代理时，
通过 `task_id` 传入该任务的 TID（例如 `task_id: "T4"`）——但只能传
Task 工具在本次会话中实际返回的 TID。子代理完成后，
系统会检查 `tasks/<task_id>/progress.md` 是否存在且具有要求的
结构——如果不存在，子代理会在终止前再获得一次写入机会。

如果 `task_id` 格式错误或指向不存在的任务，绑定会被丢弃——
子代理的发现不会记录到该任务，工具结果
会说明这一点。对于未绑定任务的临时工作，把 `task_id` 留空；此时
postStop 检查会变成空操作。

## 使用说明

- **`spawn` 与 `run` 的结果投递**：`spawn` 立即返回 actor_id，让你继续有用的工作。需要结果时使用 `wait`；主回合在结束前也会等待活动子代理。这些等待可被用户输入中断，且不会取消子代理。没有活动执行的 actor 已停止，不能仅因其存储的 status 如此说就认为仍在运行。仅仅缺乏近期活动不能证明失败。`run` 在行内等待其结果，不会重复发送完成通知。run 的等待被中断或超时后，子代理继续运行，其结果会以完成通知形式投递。
- **对持久同伴使用 `wait` 的注意事项**：`wait` 是为通过 `spawn`/`run` 启动的临时子代理设计的。持久同伴在回合之间空闲，成功后从不会产生 "done" 结果——对同伴 `wait` 会阻塞到它失败或被取消。请改用 `send` + `status` 与同伴协调。
- **`send` 语义**：发后即忘；无论接收方负载如何都会在约 5 毫秒内返回。它还会唤醒接收方——空闲子代理会基于自身历史再运行一个回合，因此 `send` 是你给子代理后续工作的方式。被唤醒回合的结果会以完成通知到达你，而不是来自 `send` 调用。当 `to_actor_id` 未知时，`send` 返回 `{inboxID: null, error: "receiver not found"}` 而不是抛出异常——请处理该错误路径。
- **子代理失败不是终局**：如果 `status`/`wait` 报告 `idle` + `failure`（包括进程重启导致的放弃），子代理通常仍能继续。优先发送后续的 `{"operation":{"action":"send","to_actor_id":"<id>","content":"<message>"}}`，然后再 `wait`/`status`。仅在 send 无法恢复它或任务需要干净状态时才重新 `spawn`。
- 总体上信任子代理的输出，但子代理只能看到你写的提示词；请据此做好简报。
