搜索原始对话轨迹：先前的用户/助手消息、工具输入、工具错误。

需要快速得到经过整理的答案时，优先使用 memory。需要原始来源时使用 history：逐字措辞、精确的工具参数/输出，或记忆摘要可能一笔带过或扭曲的细节。典型场景：
  - memory 已作答，但你必须核实或补齐精确细节
  - memory 中没有记录，但此前的会话中出现过
  - 调试"我是不是已经试过 X"这类跨项目问题

三个操作：
  - search：对文本、推理、工具输入/结果以及文件名/MIME 类型做 FTS BM25 检索（有界片段、message_id 和 part_id）
  - around：给定 message_id，显示周边消息的有界摘要
  - get：必需的 part_id 即使在索引重建期间也能读取源细节。offset 是从 0 开始、非负的 UTF-16 游标（默认 0），length 为 1–8000（默认 4000）。在 has_more 为真期间持续使用 next_offset；绝不要猜测 emoji 内部的游标。length=1 的分页可能包含一个完整的两单元代理对，以确保向前推进。Data URL 负载会被替换为稳定的附件定位符。

search 和 around 只返回摘要——要对每个 part_id 调用一次 get 获取全文。媒体永远不会自动附带：不带 attachment 的 get 会列出定位符；然后按列表再次调用 get，并恰好指定一个 attachment="inline:0" / "file:0" / "tool:0"。模型/provider 限制会被明确报告。历史中的 file:// URL 需要普通的读取权限；不会下载任何外部 URL。附件列表受预算限制；tool:N 和 inline:N 从 0 开始计数。后台索引重建期间搜索可能暂时不完整；已知 part_id 的 get 仍然可用。

默认范围是当前项目；传 scope="global" 可搜索本机上的所有项目。
