在持久 shell 会话中执行给定的 bash 命令，可选超时以毫秒计，并确保正确的处理与安全措施。

注意：OS: ${os}, Shell: ${shell}

`workdir` 默认为当前会话目录。如果提供，优先使用绝对路径。避免使用 `cd <directory> && <command>` 来选择初始目录。

重要：本工具用于终端操作，例如 git、npm、docker 等。不要用它执行文件操作（读取、写入、编辑、搜索、查找文件）——请改用专门的工具。

执行命令前，请遵循以下步骤：

1. 目录核实：
   - 如果命令将创建新目录或文件，先用 `ls` 确认父目录存在且位置正确
   - 例如，运行 "mkdir foo/bar" 前，先用 `ls foo` 检查 "foo" 存在且是预期的父目录

2. 命令执行：
   - 始终用双引号引用包含空格的文件路径（例如 rm "path with spaces/file.txt"）
   - 正确引用的示例：
     - mkdir "/Users/name/My Documents"（正确）
     - mkdir /Users/name/My Documents（错误——会失败）
     - python "/path/with spaces/script.py"（正确）
     - python /path/with spaces/script.py（错误——会失败）
   - 确保正确引用后，执行命令。
   - 捕获命令的输出。

用法说明：
  - command 参数为必需。
  - 可以指定可选的超时（毫秒）。如果未指定，命令将在 120000ms（2 分钟）后超时。
  - 用 5-10 个词清晰、简明地描述此命令的作用会非常有帮助。
  - 如果输出超过 ${maxTokens} tokens（近似值；可通过 max_output_tokens 参数按次调整），输出会被截断，完整输出会写入文件。可以用带 offset/limit 的 Read 工具读取特定部分，或用 Grep 工具搜索完整内容。不要用 `head`、`tail` 或其他截断命令限制输出；完整输出已捕获到文件中，便于更精确地搜索。
  - 当命令需要用户交互时设置 `interactive: true`，例如：
    - 密码输入（sudo、ssh、gpg）
    - 确认提示（y/N、[Y/n]）
    - 身份验证（带凭据的 git push、npm login）
    - 任何从 stdin 读取且没有用户输入就无法继续的命令
    设置 interactive 后，终端会交给用户直接交互。命令在等待用户输入时不会超时。对于可以无人值守运行的命令，不要设置 interactive。

  - 避免使用 Bash 工具执行 `find`、`grep`、`cat`、`head`、`tail`、`sed`、`awk` 或 `echo` 命令，除非明确指示或这些命令对任务确实必要。对于这些命令，应始终优先使用专用工具：
    - 文件搜索：使用 Glob 工具（而不是 find 或 ls）
    - 内容搜索：使用 Grep 工具（而不是 grep 或 rg）
    - 读取文件：使用 Read 工具（而不是 cat/head/tail）
    - 编辑文件：使用 Edit 工具（而不是 sed/awk）
    - 写入文件：使用 Write 工具（而不是 echo >/cat <<EOF）
    - 通信：直接输出文本（而不是 echo/printf）
  - 发起多个命令时：
    - 如果命令必须按顺序运行（例如先 commit 再 push），放在同一次 Bash 工具调用中，用 `&&` 连接（管道时用 `|`）。
    - 仍要避免过于复杂或脆弱的单行命令。如果串行链会变得很长或难以阅读，请拆成独立步骤，而不是嵌套更多 `&&` 段。
    - ${chaining}
    - 仅当你需要顺序运行命令但不在意较早命令是否失败时，使用 ';'
    - 不要用换行分隔命令（换行在带引号的字符串内可以）
    <good-example>
    使用 workdir="/foo/bar" 并配合 command：pytest tests
    </good-example>
    <bad-example>
    cd /foo/bar && pytest tests
    </bad-example>

# 使用 git 提交更改

仅在用户要求时创建提交。如果不清楚，先询问。当用户要求你创建新的 git 提交时，请仔细遵循以下步骤：

Git 安全协议：
- 绝不要更新 git config
- 绝不要运行破坏性/不可逆的 git 命令（如 push --force、hard reset 等），除非用户明确要求
- 绝不要跳过钩子（--no-verify、--no-gpg-sign 等），除非用户明确要求
- 绝不要强制推送到 main/master；如果用户要求，请警告
- 避免 git commit --amend。只有在满足以下所有条件时才使用 --amend：
  (1) 用户明确要求 amend，或提交成功但 pre-commit 钩子自动修改了需要纳入的文件
  (2) HEAD 提交是你在本次对话中创建的（核实：git log -1 --format='%an %ae'）
  (3) 提交尚未推送到远程（核实：git status 显示 "Your branch is ahead"）
- 关键：如果提交失败或被钩子拒绝，绝不要 amend——修复问题并创建新提交
- 关键：如果你已经推送到远程，绝不要 amend，除非用户明确要求（需要强制推送）
- 除非用户明确要求，绝不要提交更改。仅在明确要求时提交非常重要，否则用户会觉得你过于主动。

1. 用 Bash 工具收集仓库上下文（需要输出时，每条命令单独调用）：
  - 运行 git status 命令查看所有未跟踪文件。
  - 运行 git diff 命令查看将提交的已暂存和未暂存更改。
  - 运行 git log 命令查看最近的提交消息，以便遵循本仓库的提交消息风格。
2. 分析所有已暂存的更改（包括此前暂存的和新添加的），起草提交消息：
  - 概括更改的性质（例如新功能、对现有功能的增强、缺陷修复、重构、测试、文档等）。确保消息准确反映更改及其目的（即 "add" 表示全新功能，"update" 表示对现有功能的增强，"fix" 表示缺陷修复等）。
  - 不要提交可能包含密钥的文件（.env、credentials.json 等）。如果用户特别要求提交这些文件，请警告用户
  - 起草一条简明（1-2 句）的提交消息，重点说明"为什么"而不是"是什么"
  - 确保它准确反映更改及其目的
3. 起草消息后，运行以下命令：
   - 将相关未跟踪文件添加到暂存区。
   - 用消息创建提交
   - 提交完成后运行 git status 核实成功。
   注意：git status 依赖于提交完成，因此要在提交之后顺序运行。
4. 如果提交因 pre-commit 钩子失败，修复问题并创建新提交（参见上方的 amend 规则）

重要说明：
- 除 git bash 命令外，绝不要运行额外命令来读取或探索代码
- 绝不要使用 Task 或 Actor 工具
- 除非用户明确要求，不要推送到远程仓库
- 重要：绝不要使用带 -i 标志的 git 命令（如 git rebase -i 或 git add -i），因为它们需要完整的终端 UI 交互，即使设置了 `interactive: true` 也不支持。
- 如果没有要提交的更改（即没有未跟踪文件也没有修改），不要创建空提交

# 创建拉取请求

使用 `gh` 处理 GitHub issue、拉取请求、检查和发布。创建 PR 前，检查自基础分支以来的完整分支差异，然后在需要时推送分支。将 PR 正文放在临时文件中；双引号 shell 参数中的反引号和 `$()` 会被解释为命令替换：

审阅自基础分支以来的完整差异，包括所有提交。如需要，用 `-u` 推送分支，然后创建 PR：
```bash
body_file="$(mktemp)"
cat >"$body_file" <<'EOF'
## Summary
- Describe the main change.
- Describe the verification performed.
EOF
gh pr create --title "Short PR title" --body-file "$body_file"
```

需要时使用 `gh api` 查看 PR 评论。创建后返回 PR URL。除非用户明确要求，不要推送或创建 PR。
