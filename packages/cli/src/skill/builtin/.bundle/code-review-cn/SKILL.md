# 代码审查

## 审查范围

1. 先读需求和 PR 描述，理解意图
2. 看 diff，再读被修改函数的调用方
3. 看测试是否覆盖失败路径
4. 必要时运行测试、类型检查、构建

## 优先级

- P0：正确性、数据丢失、安全漏洞
- P1：并发、错误处理、兼容性、明显性能回退
- P2：可维护性、可读性、测试缺口
- P3：风格建议，默认不展开

## 检查清单

### 正确性

- 边界：空值、0、负数、超长输入、Unicode
- 错误路径：失败后状态是否一致
- 状态机：是否存在非法状态转移
- 幂等：重试是否会重复写入
- 时间、时区、精度、舍入

### 并发与数据

- 竞态、锁顺序、死锁
- 事务边界、部分失败、回滚
- 缓存一致性与失效策略
- 迁移：旧数据兼容、是否可回滚

### 安全

- 注入：SQL、命令、模板、路径
- 鉴权：越权、IDOR、租户隔离
- 密钥或令牌是否泄漏到日志、前端、错误信息
- 路径穿越、SSRF、反序列化
- 用户输入的长度、类型、编码校验

### 测试

- 是否覆盖失败路径和边界
- 断言是否真的验证行为
- 是否 mock 掉了核心逻辑
- 测试是否稳定：时间、顺序、网络

### 可维护性

- 命名是否表达意图
- 圈复杂度、重复代码、死代码
- 公共接口是否向后兼容
- 日志和错误信息是否足以排查

## 输出格式

每条问题：

- [P0/P1/P2] 文件:行
- 问题：一句话
- 为什么：会导致什么后果
- 建议：具体怎么改
- 可选：示例代码

最后给出：

- 必须修改项
- 建议修改项
- 已确认没问题的关键点
- 未覆盖或需要作者回答的问题

## 规则

- 不评论纯个人风格；有 formatter/linter 的交给工具
- 不重复 lint 已覆盖的问题
- 不提出无法落地的大重构
- 区分“事实”和“偏好”
- 除非用户要求，不直接改代码
- 找不到问题时明确说“未发现阻塞问题”，不要凑数

## 与 /review 配合

`/review` 负责取 diff 和变更范围；本技能负责审查标准和输出。用户只说“review 一下”时，先确定范围（未提交 / 分支 / PR），再按本清单执行。

## 不要做

- 只复述 diff 内容
- 把“可能”“也许”当成问题
- 用风格问题淹没真正的高风险问题
- 在没有上下文时否定作者的架构决策
