# 系统化调试

## 核心原则

1. 先复现，再改代码。
2. 一次只验证一个假设。
3. 不做猜测式修改；每个改动都要有证据。
4. 修复根因，不修症状。
5. 先写失败测试，再修复。

## 流程

### 1. 定义失败

- 期望行为与实际行为分别是什么
- 触发条件、频率、首次出现时间
- 影响范围：单用户还是全量、单平台还是多平台

### 2. 建立最小复现

- 最小输入、最短步骤、最少依赖
- 记录环境：版本、OS、时区、语言、配置、数据
- 偶发问题：统计频率，记录时间戳和请求 ID

### 3. 收集证据

- 完整错误栈，不只看最后一行
- 日志、网络请求、数据库状态、文件内容
- 用 `git bisect` 找首次引入的提交
- 性能问题用 profiler，不要靠日志猜

### 4. 缩小范围

- 二分法：禁用模块、替换依赖、缩小输入
- 在怀疑边界两侧插桩，确认数据形状
- 区分“输入错”“处理错”“输出错”

### 5. 提出假设并验证

每个假设写成：

- 如果……那么应该观察到……
- 实验：改什么、看什么
- 结果：支持还是推翻

不要同时改多个变量，否则无法归因。

### 6. 最小修复

- 只改导致失败的代码路径
- 保持行为兼容；需要时加防御
- 不顺手重构、不扩大范围

### 7. 回归验证

- 先加能复现失败的测试，确认它失败
- 修复后测试通过
- 跑相关测试、类型检查、构建
- 检查同类路径是否有相同问题

## 插桩规则

- 临时日志带统一前缀（如 `DBG-xxxx`），方便搜索和删除
- 不改变业务逻辑和返回值
- 调试完成后删除所有临时日志
- 能用断点或单步就不用日志；能本地复现就不要在生产上试

## 常见陷阱

- 只看最后一条错误，忽略第一个错误
- 忽略并发、缓存、重试、时区、编码、平台差异
- 把“没有报错”当成“没有问题”
- 修复后不写测试，问题再次出现
- 在版本或配置不同的环境里复现

## 输出格式

1. 现象
2. 复现步骤
3. 证据（日志、栈、请求）
4. 根因
5. 修复
6. 验证结果
7. 后续风险

## 何时停下来问用户

- 需要生产数据或权限
- 无法复现且缺少日志
- 修复会改变公开行为或数据格式
- 涉及第三方服务、硬件或不可控网络

## 不要做

- 为了“先让它跑起来”而吞掉异常
- 用 sleep 掩盖竞态
- 关闭测试或降低断言来让 CI 变绿
- 在没有证据时大范围重写
